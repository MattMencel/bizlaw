# Rails 8 + Inertia + Svelte, SQLite, and no LLM in the request path

The reimagined BizLaw is a browser-based, two-team legal negotiation simulation
with expressive NPC avatars, built and maintained by one person working through
coding agents. It is built in **Ruby on Rails 8** with **Inertia** driving
**Svelte** for the game view, plain server-rendered views for the instructor
console, **SQLite** on a single Fly volume, and **no LLM client in the web tier
at all** — NPC dialogue is generated offline and stored.

The three constraints that produced this are: the code is agent-written and
human-reviewed, so the binding limit is review capacity rather than typing speed;
the app is *graded coursework*, so its content must be in the accessibility tree;
and NPC dialogue must be materialized ahead of time so an instructor previews the
exact bytes students will see.

## Considered options

**Game engines (Godot, PixiJS, Phaser) — rejected on accessibility.** Godot's
threading objection has evaporated (single-threaded export has been the default
since 4.3), but Godot renders to canvas, and AccessKit's screen-reader support is
desktop-only with no web timeline. Anything inside a canvas is invisible to both
screen readers and this repo's axe-core suite. For a required course that is
disqualifying, not a polish item. Engines also foreclose layered SVG, which the
avatar work depends on.

**Rails + Hotwire alone — rejected as too thin for the game view.** A stateful
boardroom with reacting avatars and a Terms board is precisely where Hotwire is
weakest. Inertia buys a component-level animation model for the one screen that
needs it, without introducing a second API surface.

**Full-stack TypeScript — rejected on the boring half.** One language across the
authored simulation content is genuinely attractive, and XState plus Stately
Inspector is the strongest off-the-shelf answer for the instructor's event-deck
preview. But a graded course app needs dashboards, roles, exports and audit
trails, and building those from parts costs more than the preview UI saves. The
"Ruby has no first-party LLM story" argument that would have tipped this does not
survive contact with the release feed: `anthropic-sdk-ruby` is at v1.67.0 and
ships in lockstep with the TypeScript SDK.

**Managed Postgres — deferred, not rejected.** Fly Managed Postgres starts at
$38/month against roughly $2/month of compute. Rails 8 runs Solid Queue, Solid
Cache and Solid Cable on SQLite, so one volume replaces a database and a Redis.
At zero-to-two sections, the failover that $38/month buys is insurance against an
event that costs an email. Revisit at the first paying school. The cost is a
portability constraint honoured from day one: no PostgreSQL enums, no PG-specific
JSONB operators.

## Consequences

**Node survives as a build-time dependency only.** Avatars are rendered to static
SVG at build time and the output committed, so the runtime serves files whether
the art stays `@dicebear/core` or becomes a commissioned reskin.

**Auth is WorkOS AuthKit**, free to 1M MAU — email/password, magic link and Google
social in one tier. Enterprise SSO is $125/connection/month and is YAGNI: a school
that demands SAML can pay for it, and adding it later is a dashboard change.
Identity and enrollment are separate layers — AuthKit vouches for the human, the
Instructor's join code puts them in a Section.

**The engine is Apache-2.0; Cases are not.** The moat is authored case content —
Terms, Par values, Exhibits, event decks, generated dialogue — plus the
cross-semester calibration data that never ships at all. The engine lives in this
public repo (unlocking unlimited GitHub Actions minutes); Cases live in a private
repo under a proprietary content licence. Self-hosting is YAGNI, but the Case
format carries an identifier and a licence field and loads through one seam that
could later be a fetch — a shape that is free now and expensive to retrofit.

**Billing and multi-tenancy are out of scope** for the current design effort. The
only constraint carried forward is that the schema holds a tenant boundary from
day one, so commerce is later a feature rather than a migration.

**The LLM is a build-time tool.** Dialogue is generated by a rake task at
case-authoring time and stored against the state-machine node that triggers it;
the request path is pure Rails against stored rows. This removes the API key from
the web tier, makes the instructor preview exactly honest, gives grading a stable
artifact, and means a vendor outage cannot stop a class. Calls go through
**OpenRouter** using the official `openai` Ruby gem with `base_url` pointed at
`https://openrouter.ai/api/v1`, so the model is a config string rather than a
stack commitment:

```ruby
client = OpenAI::Client.new(api_key: ENV.fetch("OPENROUTER_API_KEY"),
                            base_url: "https://openrouter.ai/api/v1")
client.chat.completions.create(
  model: "z-ai/glm-5.3-flash", messages: [...],
  request_options: { extra_body: { provider: { zdr: true, data_collection: "deny" } } })
```

`zdr: true` and `data_collection: "deny"` are not optional: the payload is the
authored case content, which is the product. Provider pinning also answers any
data-residency objection to an open-weight model, since twenty upstream providers
serve GLM and several are US-hosted. Record the model id and prompt version on
every generated line. Model *choice* stays open — at roughly $21 per cohort on
Haiku 4.5 and ~$3 on GLM-5.3-Flash, cost is not a design driver, and dialogue
quality is the last thing to economize on.

**The boundary runs both ways: the model never reads student prose.** The
generated-dialogue rule above governs what the model writes; this governs what it
is given. Offer notes, deliberation threads, Peer Evaluation lines and anything a
Team wrote are never sent to a model — not as a grading digest for the instructor,
not as a characterisation of what a team argued, not as a safety pass before a
teammate reads a message.

The load-bearing reason is consent rather than architecture. `zdr: true` is bought
above to protect authored case content, which is the professor's work and the
product; it is not a promise about the students, whose prose is an educational
record this product has no agreement to send to a vendor. The architectural reason
corroborates — student text does not exist at case-authoring time, so any read is
necessarily a runtime call into a web tier that holds no API key — but it is the
weaker of the two, because a background job satisfies it and the consent reason
survives any change of architecture.

The rule reaches past model vendors to any processor that receives data
incidentally — error tracking, analytics, log aggregation — as a constraint on the
payload rather than a ban on the tools: run them, with student prose scrubbed from
what leaves. The host is a separate case, since data on the application's own
volume is tenancy rather than disclosure. Build no scrubbing framework in advance;
apply the rule when a telemetry vendor is actually chosen.

Enforce it structurally rather than by review, matching the case-import gate: the
LLM client is required only from the generation rake task's path and is never
autoloaded into the web tier, with a spec asserting it, so a runtime read fails to
load rather than failing a code review.
